# Python, Rust или C: что выбрать для серверной части

Вопрос из обсуждения: «серверную часть можно написать на Rust, хотя
советуют остаться на C». Разбор по существу.

## Где реально тратятся ресурсы

Профиль нагрузки туннеля: network-bound. На один MTProto-пакет CPU
делает AES-256-CTR (десятки ГБ/с на современном CPU с AES-NI) и
копирование байтов. Даже на самом дешёвом VPS узкое место — канал и RTT
до Telegram, а не язык. Замеры, которые имеют смысл:
задержка пересылки (≈ +0.1–0.3 мс на hop против прямого TCP),
RAM/бинарник, CPU на ГБ трафика.

## Сравнение

| Критерий | Python (текущее ядро) | Rust | C |
|---|---|---|---|
| Алгоритмическая скорость | достаточно (AES нативный через `cryptography`) | максимальная | максимальная |
| RAM на процесс | ~40–70 МБ | ~5–10 МБ | ~2–5 МБ |
| Безопасность (TLS-стек, парсинг чужих пакетов) | зрелые библиотеки | зрелые (rustls), memory safety | ручная работа с OpenSSL/памятью — источник CVE |
| Кроссплатформенность | win/mac/linux из коробки | cargo → один бинарник на каждую цель | кросс-компиляция мучительная |
| Скорость разработки/поддержки форка | высокая (весь апстрим на Python, патчи мержатся) | средняя | низкая |
| Бинарник для раздачи | PyInstaller ~10–20 МБ | ~2 МБ статически | ~1 МБ |

**Почему «советовали C»**: традиция сетевых демонов (nginx, haproxy).
Но здесь 99% кода — прикладная логика протокола (obfuscation, fake TLS,
WS-кадры, фолбэки), и писать её на C означает повторять чужие CVE.
Rust даёт ту же скорость и вес, плюс безопасность памяти и удобную
кросс-компиляцию — это замена C без его рисков.

## Что выбрано в форке

1. **Python как основа** — поверх оттестированного ядра апстрима
   (10.9k звёзд, сотни issue-фиксов): fake TLS, CF-фолбэки, H2-медиа,
   пулы — всё уже работает и мержится.
2. **Rust-прототип** (`rust/`) — проверка гипотезы «один бинарник»:
   - реализовано: MTProto-фронтенд (мульти-секреты, dd), SOCKS5-мост
     (plain + obfuscated), WS-туннель с пиновым IP и SNI,
     реенкрипция с нарезкой по пакетам;
   - `cargo test` — 16 unit-тестов (хендшейк, сплиттер, SOCKS5,
     конфиг), кросс-валидирован с Python-клиентами
     (`DC2 -> WS hit` на реальном шлюзе);
   - release-бинарник ≈ 1.8 МБ (opt-level=z, lto, strip);
   - TODO до parity: ee-секреты (FakeTLS ServerHello), CF-фолбэки,
     пулы WS-соединений, PROXY protocol, тестовые DC.
3. **C не используется** и не потребуется: единственное потенциально
   «горячее» место — AES, и оно уже нативное (RustCrypto/`cryptography`
   оба используют AES-NI).

## План миграции (если Rust-прототип дорастишь до parity)

-parity = golden_connect OK на всех трёх маршрутах + суточный soak:

1. Публиковать `tgws-rs` как второй бинарь в релизах (`tgws-rs_linux_amd64`).
2. Ключевая выгода — resource-constrained VPS (256 МБ) и раздача без
   установки Python-стека.
3. Держать Python-версию основной: апстрим не стоит на месте
   (маскировка, новые DC-карты), и дифф мержить проще в Python.
