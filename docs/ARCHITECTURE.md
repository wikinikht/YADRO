# Архитектура: как tg-ws-proxy-server работает

## Схема

```
┌─────────────────────────── VPS (RF) ───────────────────────────┐
│                                                                 │
│  Telethon/Pyrogram бот        Telegram Desktop / любой клиент   │
│        │ socks5 :1080                │ MTProto proxy :1443      │
│        ▼                             ▼                          │
│  ┌────────────────── tgws-server (один процесс) ─────────────┐  │
│  │  SOCKS5-мост            MTProto-фронтенд                  │  │
│  │  (self-obf транспорт)   (FakeTLS secret, dd/ee)           │  │
│  │        │ реенкрипция +         │ снятие proxy-транспорта  │  │
│  │        ▼ доставка по пакетам   ▼                          │  │
│  │           свежий obfuscation-init на DC                  │  │
│  └──────────────────────────┬────────────────────────────────┘  │
└─────────────────────────────┼───────────────────────────────────┘
                              │ TLS (SNI kws2.web.telegram.org)
                              │ WebSocket /apiws, первый кадр = init
                              ▼
                 149.154.167.220:443  ← IP в белых списках ТСПУ
                 (веб-шлюз Telegram, обслуживает DC2/DC4)
                              │
                              ▼
                    MTProto datacenter (DC2 / DC4)
```

## Почему это проходит блокировки

1. **IP в белом списке.** ТСПУ блокирует/душит прямые TCP-соединения к
   MTProto-датацентрам (149.154.x.x). Но IP `149.154.167.220`
   обслуживает веб-версию Telegram (webk/webz в браузере) и потому
   остаётся доступен — [объяснение автора апстрима]
   (https://github.com/Flowseal/tg-ws-proxy/discussions/180).
2. **SNI узнаваемый.** Соединение — обычный TLS к домену
   `kws2/kws4.web.telegram.org`: инспекция содержимого бесполезна
   (MTProto-полезная нагрузка внутри WS зашифрована), а по IP блокировать
   нельзя — «положите» этот IP и ляжет web.telegram.org.
3. **Внутри WebSocket — стандартный MTProto.** Первым бинарным кадром WS
   отправляется 64-байтовый obfuscation-init, дальше кадры = MTProto
   пакеты. Шлюз веб-версии принимает их как «обычный веб-клиент».

## Протокол по слоям

### 1. MTProto-фронтенд (порт 1443) — вход для MTProto-клиентов

Клиент подключается как к обычному MTProto-прокси:

- секрет `dd<32hex>` — голый obfuscated-транспорт;
- секрет `ee<32hex><домен-hex>` — FakeTLS: клиент шлёт настоящий вид
  TLS ClientHello (SNI = домен из секрета), прокси проверяет подпись
  HMAC-SHA256 по секрету, отвечает синтетическим ServerHello и дальше
  читает obfuscated-init из «TLS-записей». Для DPI это HTTPS-сессия.

Внутри init (64 байта):
`init[8:40]` = prekey, `init[40:56]` = IV,
ключ клиента = `SHA256(prekey + secret)`;
`init[56:60]` = транспортный тег (`EFEFEFEF` abridged, `EEEEEEEE`
intermediate, `DDDDDDDD` padded), `init[60:62]` = signed DC id —
всё это XOR-нуто с keystream AES-256-CTR. Так прокси узнаёт **DC и
транспорт**, не имея ключей клиента.

### 2. Пере-шифрование к DC

Прокси генерирует **свежий** obfuscation-init (`_generate_relay_init`)
с тем же тегом транспорта и DC id, открывает TLS→WS к
`kws{dc}.web.telegram.org` **через пиновый IP** из `dc_ips` (не через
DNS — в РФ DNS могут подменять), отправляет init первым кадром и дальше:

- клиент → WS: расшифровать клиентский транспорт → нарезать на пакеты
  по MTProto-фреймингу (`MsgSplitter`) → зашифровать транспортом DC →
  один пакет = один WS-кадр;
- WS → клиент: кадр = полный MTProto-пакет → расшифровать → зашифровать
  клиентским (реверс-ключи) транспортом → записать в TCP.

Клиент и DC честно общаются MTProto end-to-end; прокси видит только
транспортную обфускацию, но не содержимое сессии (авторизация, чаты).

### 3. SOCKS5-мост (порт 1080) — вход для клиентских библиотек

Telethon/Pyrogram умеют socks5, но не MTProto-proxy. Мост:

1. принимает SOCKS5 CONNECT (например, к `149.154.167.51:443`);
2. читает голову клиентского потока:
   - `0xEF` — plain abridged (Telethon по умолчанию, без обфускации!);
   - `0xEEEEEEEE` — plain intermediate;
   - иначе 64-байтовый self-obfuscated-init (Pyrogram всегда
     обфусцирует; ключи лежат в самом init — секрет не нужен);
3. DC берёт из **цели CONNECT** (в plain-транспортах init не содержит
   DC id — это важный нюанс, найденный при отладке);
4. строит контекст: plain-транспорты идут через identity-шифр с
   клиентской стороны, obfuscated — через собственные ключи init;
   к Telegram — свежий relay-init, как у MTProto-фронтенда.

Бот ни о чём не знает: он думает, что подключился к датацентру напрямую.

### 4. Резервные маршруты (наследие апстрима)

Если WS-шлюз недоступен (не 101): CF-прокси домены сообщества →
свой Cloudflare Worker (`--cfproxy-worker-domain`) → прямой TCP к DC
(из РФ обычно заблокирован). Медиа мультиплексируется через HTTP/2
(`cf_h2`). Всё это работает и в форке — см. upstream docs.

## Что важно для РФ-VPS

- DNS подменяют → **пиновый IP**: соединение идёт на `dc_ips`, SNI
  подменяется на kws-домен (upstream `RawWebSocket.connect(host=ip,
  domain=...)`).
- Проверка доступности маршрута — `tgws-server doctor`: TLS+Upgrade до
  101 с пинового IP и есть тест «белого списка».
- Кэшированные CF-домены апстрим подтягивает сам (GitHub-лист).

## Ограничения

- WS-шлюз обслуживает **только DC2/DC4** (остальные DC через fallback).
- Bot API (`api.telegram.org`) — это HTTPS, **не** MTProto: через
  WS-туннель он не проходит. Решения — в [BOTS.md](BOTS.md).
- FakeTLS-домен стоит выбирать «нейтральный» и существующий — прокси
  замеряет реальные размеры TLS-записей этого домена для камуфляжа.
